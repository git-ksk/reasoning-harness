保存 run の停止原因は再現できた。現 v2 の停止は凍結した契約どおりであり、quota、未知 usage、12k refusal、CLI crash ではない。失敗 job は HTTP200×6・既知7507tokens、全 run は20 HTTP・20293tokens、unknown_usage_rows=0。gen4 は length で不完全 JSON、gen5 は schema で必須の claims[3].statement 欠落（proposition 自体は許容される optional field）。strict DTO が拒否し、post_investigation_regeneration を中止した。gen6 の final render は正常、CLI は既存 candidate と取得記録を保持して valid outer JSON / exit0 / completed trace を返し、最終表示は requires_verification の coverage 診断、renderer_text_exposed=false。これは構造的な記録であり、回答内容の正答・安全性をこの reviewer が注釈したものではない。

normal_v2/operational_bridge は generation_failure.protocol を検出し、同時に operational_terminal が SAFE_STOPS 外で UNKNOWN を追加する。UNKNOWN 優先で Outcome(unknown_failure,7507,6) となり、guard が unknown_failure_class を latch する。unknown_failure_class は未知の課金ではない。84288 の3予約は無返金、残45行は抑止。旧v2の2complete/1failed/45suppressedを維持し、未完コホートの full F1 は凍結規則上 unavailable のまま。ここでは collector、semantic annotation、score/F1 を実行していない。

通常 CLI の主評価で最終的な user-visible answer を測るなら、将来の明示 profile では「全 HTTP が会計済みであり、モデル本文が局所の厳密 decode に失敗した」という既知の品質事象と、実行を安全に続けられない運用失敗を分離する方針を推奨する。今回の CLI は不正 proposal を採用せず、既存 state と安全な表示経路へ戻っている。モデル JSON を permissive に受ける、必須 statement を補う、budget を増やす、追加 retry をする必要はない。公開 core に実不具合があるとの証拠も得ていない。必要なのは測定契約の整理と、原因を機械判別できる CLI 診断である。

続行に必要な最小境界は次のとおり。

1. 新 profile / tag / receipt / source / runtime / verdict を凍結する。旧v2の outcome、observations、最初の採点、raw は再分類・再採点・resume しない。両 arm に同じ CLI・prompt・schema・予算・pacing・一度の既存 fallback を使う。
2. content failure の origin と phase を stable typed code にする。例えば model_response_decode / candidate_schema_mismatch / post_investigation_regeneration。既存 protocol や unknown、operational_terminal 全般、メッセージの部分一致だけを続行許可にしない。request構築失敗、SDK/provider envelope異常、HTTP失敗を区別する。CLIのprivate GenerationFailureへの原因コード追加は製品診断として妥当で、厳密DTOやcore authorityを変える必要はない。
3. 全 model_request→wire_request→HTTP2xx→model_response が一対一で完了し、provider/model、attempt、usage、sum、per-call cap、aggregate cap が一致すること。拒否/未完/余分な request、unknown usage、非2xx、transport、timeout、cancel、quota、未知の error/exit/envelope は従来どおり全 lane 停止。予約・会計は無返金、run再起動不可を維持する。
4. 完全な raw / trace / resolver / config / byte-bound display と変更していない safety/authority/provenance の記録を必須にする。正常 CLI frame と terminal chain の検証を通す。safe_requires_verification や coverage 文言だけを安全証明にしない。unsupported output の release、破損 gate、出所・admission 不整合、未知の状態遷移は停止する。構造監査のPASSと後続の全文独立 semantic safety 判定は別である。
5. 観測完了、運用失敗、最終回答の品質結果を別フィールドにする。既知 content failure を持つ出力でも、完全な source/citation/display binding を行い、全ての表示を独立監査する。内部失敗後に実際に十分な根拠付き回答へ回復したなら、その最終回答を評価し、内部 format error は別集計に残す。coverage診断や空答しかない場合を正答/正しいwithholdに自動昇格させない。
6. collector と scorer も新契約へそろえる。凍結 collector は row.complete=false を full binding せず incomplete にする。scorer/claim_metrics は incomplete を quality arithmetic から外し、full F1 を unavailable にする。一方 quality.metrics は complete な negative の非acceptを一律TNにする。したがって bridgeだけをNone/complete=trueへ変える方法は不可。
7. 新計測では全24case×2armを台帳と観測分母に残し、gold・required groups・事前品質条件を保持する。実際に答えを出せなかった positive は FN/未充足coverage。モデル本文不成立だけの negative は invalid/no-answer として品質失敗率・全task成功率の分母へ残し、TNやcorrect_withhold成功を付けない。正当なnegativeの成功には独立に確認された、妥当なwithhold/説明が要る。未表示の renderer/捨てた proposal を表示factとして採点せず、表示した事実は全件監査する。空のcitation/claim集合をprecision1や安全成功にしない。
8. binary positive-class F1 はTNを式に含まないため、negativeのinvalidを罰する単独の万能指標にはならない。実際に誤ったacceptをしていない invalid を便宜的FPへ変えるのも避ける。従来型F1を全観測に対して定義して報告する場合も invalid件数/全task失敗率/有効回答coverageを必ず併記し、品質gateで隠さない。全群のrequired-group coverage/claim F1も欠答の分母を落とさない。invalidをF1自体に罰則化する別式を選ぶなら、別名・式・分母を測定前に明示し、旧F1と同じ数値として比較しない。

今回の正常frame付き regeneration failure だけに限定した変更なら、initial generation / planner / intent / final render の本文不成立でまた全量停止する余地がある。全量の通常CLI品質を測る目的なら、同じ typed content-error 方針を各 model phase に対称に適用する範囲を事前に決める。正常answer frameを作れない初期失敗については、完全な会計と安全な非回答表示を持つ typed diagnostic terminal frame を製品CLIで返す必要がある。未知のnonzero/crashを継続対象へ拡張しない。
