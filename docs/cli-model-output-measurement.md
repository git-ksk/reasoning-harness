# Prospective ordinary-CLI model-output measurement

Tracked in [Issue574](https://github.com/git-ksk/reasoning-harness/issues/574). Declared 2026-10-31, before any v3 model execution. This policy applies only to a new separately frozen profile. Historical runs, inputs, annotations, first scores, receipts and tags remain immutable. See the [stopped v2 evidence](../evaluation/cli-normal-real24-development-v2-results/README.md).

The ordinary CLI is evaluated on the answer a user receives. A fully accounted model response that fails local strict decoding is an observed quality event, distinct from a transport or accounting failure. Add private typed origin and phase diagnostics only where the adapter returned successfully and local model-response parsing failed. Phases cover initial candidate, regeneration, investigation plan/intent/action and final rendering. Request construction, provider envelopes, authorization and policy rejections are not model-output errors. A later budget, unknown-usage or transport failure must override and clear any permissive diagnostic.

Continuation requires an independently reviewed new runtime, an expected typed terminal envelope, complete immutable raw/trace/display/source binding, and matching provider/model/attempt/usage records for every request. All HTTP attempts must be completed successful responses with known usage within unchanged call and aggregate limits. Unknown diagnostics, crashes, non-2xx, quota, unknown usage, timeout, cancellation, budget exhaustion, unsafe output and authority/provenance mismatch retain strict global stopping. A protocol label, diagnostic phrase or exit code alone never authorizes continuation. The private typed diagnostic does not change public Core contracts, strict schema acceptance, fallbacks, prompts or runtime limits.

Observation completeness and answer quality are separate fields. Independent annotation covers the actual byte-bound display, claims, citations and sources even when an internal failure occurred. A fully recovered valid final answer is graded normally and its recovered formatting error is reported separately. A pure terminal diagnostic, empty output or unusable answer is quality `invalid`; it cannot become a correct abstention automatically.

- Positive terminal invalid is FN and retains missing required claim groups in the claim denominator.
- Negative terminal invalid is an invalid/error outcome, never TN or correct-withhold. It remains in the full observed denominator (24 cases per arm), invalid rate and class-specific counts.
- Unsafe displayed assertions override invalid status: negative FP or positive FN, plus the hard safety violation. Never hide a safety failure as an error-only row.
- Standard positive-class F1 excludes TN mathematically. Report F1/P/R together with TP/FP/FN/TN, invalid counts/rate, observed count, valid-answer coverage and task-success rate. Do not present F1 alone as the overall pass criterion or invent FP solely to penalize a negative invalid.
- Any terminal invalid blocks quality GO. Case and claim F1 >=0.90, precision >=0.95, recall >=0.85, hard safety violations 0, full citation fidelity/coverage, no regression and the existing efficiency gates remain required. No threshold is relaxed.

Before live use, connect collector, annotator and scorer under the same new contract. Check the actual scheduler without HTTP: accounted typed model-output failure retains its charge and advances; operational/accounting/safety failures suppress the next job; unknown or forged origins do not advance. Verify initial/final error paths as well as regeneration. New independent source review, exact runtime/image acceptance, current readiness and a new genuine receipt/tag precede a single new 48-job Mistral run. Google/Groq remain held; auxiliary API verification stays model-free. These consumed cases remain engineering diagnostics; fresh independent accuracy acceptance and CLI adoption remain separate.
