# ADR-0001: インターフェースとパッケージングの境界

- Status: Accepted
- Date: 2026-08-29

## 背景

このプロジェクトは、プロンプト集でも、外部エージェントが任意に呼び出せるツールでもなく、ネイティブな推論ハーネスである。その主な役割は、確率的モデルを取り巻く実行プロトコル、すなわち状態遷移、検証、検証パス、受け入れポリシー、リトライ／予算ポリシー、そして最終的な認識論的ステータスを担うことにある。

インターフェースとしては、ライブラリ API、CLI、評価ランナー、デスクトップ UI、MCP サーバーなどが考えられる。これらをすべて同等のプロダクト面として扱うと、信頼境界が曖昧になり、UI や統合に関する関心事がコアの意味論へ漏れ込むことになる。

## 決定

プロジェクトでは、次の責務順序を採用する。

1. **Native Harness Runtime** — プロダクト／コアの正しさの境界。
2. **CLI** — 最初にサポートするユーザー向け・自動化向けインターフェース。
3. **Eval Runner** — 第一級の研究・リグレッション用インターフェース。
4. **Desktop UI** — 後回しにする、人間による調査用の薄いクライアント。
5. **Embedding API** — ランタイム契約が安定した後にサポートする。
6. **MCP adapter** — 任意かつ後回し。正しさのために決して必須にしない。

ランタイムは、交換可能な `ModelAdapter` を通じたモデル呼び出しを所有する。モデルはハーネス内部の候補生成器であり、ハーネスのループ自体を所有しない。

## ランタイムの境界

概念的には、すべてのインターフェースが1つの操作へ集約される。

```ts
run({
  input,
  model,
  passes,
  policy,
}): Promise<ReasoningArtifact>
```

正確な公開 API は v0.x の間に発展し得るが、次の所有権ルールは安定している。

- ハーネスが所有する入力はタスクと証拠を提供する。モデル候補が信頼済みの証拠を作成することはできない。
- モデルが提案した強い認識論的状態は、最終的な権威ではない。
- 実行順序はランタイムが所有する。
- ランタイムは各パスの後に状態を検証する。
- ランタイムは明示的なポリシーに従い、`accept | reject | unknown` を決定する。
- モデルアダプターは、バリデーターや受け入れゲートを迂回できない。
- レンダラーは認識論的ステータスを格上げできない。
- インターフェースはコアの推論意味論を再定義できない。

## インターフェースの責務

### Native Harnessランタイム

所有するもの:

- `ReasoningArtifact` と、関連する型付き中間状態。
- 認識論的状態の遷移。
- 決定論的バリデーター。
- 推論／検証パスの実行。
- モデルアダプターのライフサイクル。
- リトライ、タイムアウト、検証予算のポリシー。
- 受け入れ／拒否／unknown の決定。
- 決定論的オラクルとの統合。

所有しないもの:

- ターミナルへの表示。
- デスクトップ上の表示。
- プロバイダー固有のプロダクト UX。
- MCP のディスカバリー意味論。

### CLI

CLI は、対話的に使え、シェルパイプラインや CI でも利用でき、別のオーケストレーション層を導入せずに済むため、最初にサポートするプロダクト面である。v0.1.0 ではまず構造化された契約を公開した。その基盤の上で、主な人間向けの方向性は、内部で同じランタイム境界を構築・通過する AI バックの自然言語コマンドである。構造化 JSON コマンドは削除・迂回されるのではなく、高度な利用、統合、デバッグ用のサーフェスとして引き続きサポートする。

初期コマンドの意味論:

```text
run       ハーネスのワークフローを実行する
verify    既存の reasoning artifact を検証する
explain   対象読者／スタイル向けに検証済み artifact を描画する
eval      fixture／ベンチマークスイートを実行する
```

コマンド名は v0.x の間は暫定的だが、責務の境界は暫定的ではない。

CLI の要件:

- 機械可読な JSON 出力を利用できること。
- 人間可読な出力だけを唯一の表現にしないこと。
- 構造上またはランタイム上の失敗では、ゼロ以外の終了ステータスにすること。
- 認識論的な `unknown` は、プロセスの失敗と自動的にみなさないこと。
- CLI フラグはポリシーを設定するが、不変条件の検査を迂回してはならない。

### 評価ランナー

評価ランナーはテストヘルパーではなく、第一級の存在である。ハーネスの変更が、モデルのマーケティング上の主張とは独立して、挙動を改善したのか悪化させたのかを測定するために存在する。

所有するもの:

- fixture の読み込み。
- ベースラインと候補の比較。
- 決定論的メトリクス。
- アダプターが公開する場合のトークン数／レイテンシ／コストの観測。
- リグレッションのしきい値。
- ハードメトリクスと、ソフトなモデル判定メトリクスの明示的な分離。

評価ランナーは CLI と同じネイティブランタイムを使用する。

### デスクトップUI

デスクトップアプリケーションは、ランタイムと artifact 形式が GUI なしでも有用になるまで後回しにする。

想定する役割は、人間による調査とレビューである:

- claim／evidence グラフの可視化。
- 仮定と unknown の調査。
- パスのタイムラインと拒否理由。
- 実行／モデル／ポリシー間の比較。
- ポリシーが許す場合の明示的な人間レビュー。

デスクトップアプリは、ネイティブランタイム上の薄いクライアントであり続けなければならない。独自の隠れたプロンプトフロー、バリデーター実装、競合するステートマシンを持ってはならない。

### 埋め込みAPI

内部の Rust crate 境界によって組み込みはすでに可能だが、安定した公開ライブラリ API は v0.1 の目標ではない。公開互換性の約束は、実際の CLI／eval 利用によって正しいランタイム契約が明らかになった後にのみ行う。

安定化した際には、Embedding API は同じランタイム意味論を公開すべきであり、利用者が検証や受け入れポリシーを省略できる低レベルの近道を公開してはならない。

### MCPアダプター

MCP は引き続き任意であり、正しさの境界の外側にある。MCP を主たるプロダクトにしないという当初の決定は変わらないが、v0.3.0 のロードマップでは現在、アダプターの役割を2つに区別している。

1. **MCP as an acquisition transport (#176):** Reasoning Harness は、既存の `ResolutionResolver` 境界を通じて、許可リストにある読み取り専用 MCP ツールを呼び出せる。ツール結果は `AcquiredEvidence` にすぎず、ハーネスが所有する受け入れと、強い権威が必要な場合の別個の信頼済み検証を引き続き必要とする。
2. **Reasoning Harness as an MCP product surface (#180):** 外部エージェントは、Rust-only の `reason-mcp` アダプターを通じて、選択されたフルランタイム操作を呼び出せる。アダプターはサポート対象のネイティブ `reason` 実行ファイルへ委譲し、バージョン付きプロダクト JSON を変更せずに返す。これは引き続き任意の下流機能であり、v0.3.0 のブロッカーではない。

MCP の呼び出し元は、ツールを呼び出すかどうかを制御する。そのため MCP サーバーだけでは、呼び出し元エージェントのループ全体に対して、このプロジェクトのネイティブな正しさのプロセスを強制できない。

結果:

- MCP は統合／取得アダプターであり、コアのハーネスではない。
- MCP resolver の結果は、信頼済み証拠や receipt へ自ら昇格できない。
- MCP ツールがフルネイティブランタイムを呼び出せるのは、サポート対象のプロダクト境界を通じた場合だけである。
- MCP ツールは、1回のツール呼び出しが成功しただけで、呼び出し元の推論全体が検証済みだと主張してはならない。
- MCP ツールのスキーマに合わせることだけを理由に、v0.x のコア API を歪めない。

## パッケージング戦略

具体的な利用者のニーズが生じる前に、モノレポや複数の公開可能パッケージを導入しない。

このリポジトリは、コード上にすでに存在する所有権の境界を持つ小規模な Cargo workspace である。

```text
crates/reasoning-harness-core/   runtime, IR, validators, passes, eval primitives
crates/reasoning-harness-cli/    native `reason` executable
crates/reasoning-harness-providers/ provider-specific HTTP adapters
examples/                        executable artifacts
docs/                            architecture, ADRs, research notes
```

追加の provider、oracle、desktop、統合用 crate は、実際に独立した依存関係または所有権の境界を持つ場合にのみ追加する。概念上のモジュールを写すだけの目的で workspace を拡大してはならない。

独立したバージョニングや外部組み込みによって価値が生じるなら、将来のパッケージ分割は認める。パッケージの構成は正しさのモデルの一部ではない。

## モデルプロバイダーのポリシー

プロバイダー SDK は、信頼済みコアの意味論に入れてはならない。

プロバイダーアダプターがしてよいこと:

- 候補生成リクエストを送る。
- 候補出力と利用量メタデータを返す。
- プロバイダーのエラーを正規化された形で公開する。

プロバイダーアダプターがしてはならないこと:

- claim を検証済みと印付けする。
- 必須のパスを迂回する。
- 最終的な受け入れを決定する。

これにより、低コスト、無料枠、ローカル、プレミアムのモデルを同じハーネスプロトコルの下で比較できる。

## 却下した代替案

### プライマリプロダクトとしてのスキル

スキルは主にエージェントへ指示とコンテキストを提供するものだから却下した。指示に従うか、どの程度忠実に従うかは、依然としてエージェントが所有する。

### プライマリプロダクトとしてのMCP

MCP は外部エージェントへ能力を提供するものであり、そのエージェントの実行ループ全体や受け入れポリシーを所有しないため却下した。

### デスクトップファーストのアーキテクチャ

推論プロトコルより先に UI の関心事が成熟し、研究自動化や CI が難しくなるため却下した。

### パブリックライブラリファーストのアーキテクチャ

CLI と eval のワークフローが検証する前に初期の公開 API 互換性が抽象化を固定してしまうため却下した。

## 結果

Positive:

- 正しさの意味論に所有者が1つだけ存在する。
- CLI と CI によって、ハーネスを安価かつ再現可能に成熟させられる。
- モデル／プロバイダーの実験を交換可能なまま維持できる。
- 将来のデスクトップ UI は意味論を発明するのではなく、安定した artifact を可視化できる。
- MCP をプロジェクトのアイデンティティを変えずに追加できる。

Costs:

- デスクトップの使いやすさが実現するのは後になる。
- 公開組み込み互換性を意図的に遅らせる。
- v0.x 初期の研究では、一部の統合が CLI を shell out する必要がある場合がある。
