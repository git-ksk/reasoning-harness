# 公開区分・リリース条件・候補版からの昇格

日本語 | [English](release-policy.md)

## 分けて決めること

| 判断 | 意味 |
| --- | --- |
| 版番号・互換性 | `0.x`は公開APIが今後変わる段階です。既存machine契約IDの約束は維持します。GitHubのプレリリース指定が自動的に必要になる意味ではありません。 |
| 公開区分 | 通常リリースは、宣言した範囲の必須条件を満たした公開版です。プレリリースは、具体的な未完了条件と昇格条件を持つ候補版です。 |
| 配布範囲 | Engineソース、Reason CLIの配布、下流への採用は別の成果物です。Engineソースのみでも通常リリースにできます。 |
| 証跡・制約 | 決定論的・合成データ・live-provider・実機・実ユーザーの検証範囲を明記します。通常リリースへの変更で未実施の検証が完了扱いになることはありません。 |

## 通常リリースの条件

公開または昇格前に、レビュー済みリリースPRへ次を記録します。

1. 正確な版番号・tag・commit・CLI/Engineの組み合わせ・サポート範囲。
2. その範囲に必要な検証と、正確な候補に対する結果。Engine動作変更には対象の正しさ・回帰検証、CLI配布には追加でpackage・provenance・install/update/rollback・該当する実機確認が必要です。必須のlive・実機検証を通常CIだけで代替しません。
3. 宣言した範囲内で必須acceptanceの未完了や公開を妨げる既知不具合がないこと。任意の研究・保留機能は分けて記載し、実装済みとは扱いません。
4. 互換性変更、測定済みの範囲、受け入れた残存制約。
5. exact-head CIの成功、マージ後ソースの確認、過去tag・凍結観測・公開assetの維持。

`0.7.1`のようなsuffixなしの版番号を使い、GitHubは`prerelease=false`にします。v1.0前の互換性制約は継続します。v1.0には公開API・互換性の明示的な判断が必要で、GitHubの表示変更だけでv1.0相当の安定性を宣言しません。

## プレリリースの条件と解除条件

`0.8.0-alpha.1`・`0.8.0-beta.1`・`0.8.0-rc.1`などを使い、packageとtagのsuffixを一致させます。GitHubは`prerelease=true`にします。候補版の公開前に、リリースノートへ次を明記します。

- 目標とする通常リリースの版番号と範囲。
- 未完了の必須検証・既知blockerと追跡リンク。
- 各項目を完了と判断する結果、および通常公開への昇格条件。
- 検証対象commit、候補版の評価用途と利用制約。

0.xであること、Engineソースのみであること、CLI未採用、任意の未実証仮説を理由に、無期限のプレリリース扱いにしません。必須条件として設定した項目は、結果を受け入れるか、範囲変更を明示してレビューするまで公開条件として残します。

通常の順序は、目標範囲の検証を完了して`0.8.0-rc.1 → 0.8.0`です。最終package/tagは別の固定座標とし、候補tag・観測を保持します。suffixなしの版を公開した後で実装を変更した場合は、過去tagの差し替えではなく新しい版番号を使います。

## GitHubの表示・asset・Latest

GitHubでは固定したtag・assetを維持したまま、プレリリース表示と説明文を変更できます。既に受け入れた同一内容の区分訂正は、再ビルド・retag・asset差し替えなしで行い、理由と証跡をノートへ残します。必須検証が未完了の版を、表示変更だけで通常公開へ昇格させません。

`Latest`はEngine/CLI共通のリポジトリ全体の入口です。通常のサポート対象**CLI配布**で明示指定し、プレリリースと**Engineソースのみ**では`latest=false`を要求します。ただし、その指定だけで共通の`/releases/latest`からEngineを除外できる保証はありません。2026-10-13の0.7.1通常公開後、この指定でも同入口は`engine-v0.7.1`を返しました（変更前は404）。

この混在リポジトリの共通Latest入口でCLIバイナリを選びません。既存CLIのlifecycle探索は、公開済みの`reason-v*`からSemVer候補suffixのない版だけを選び、native installerは明示・固定したCLI tagを使います。install/updateは署名済みCLI/Engine組み合わせも検証します。GitHubのLatestにEngineが表示されても、配布CLIがそのEngineを採用した意味にはなりません。

CLI公開workflowはmajor番号ではなくSemVerの候補suffixから公開区分を決めます。`+build-42`などのbuild metadataはプレリリースの理由になりません。suffixで決めるのは公開flagで、範囲・検証完了の承認はリリースPRが担います。

## Engine 0.7の履歴と今回の判断

- `engine-v0.7.0`は`5c7682d988c18a5a7e7a1954bd2a369cad2e9070`で、suffixなしの版番号と従来のGitHubプレリリース表示で公開しました。その履歴を維持します。`0.7.0-rc.1`という名前の候補版ではありませんでした。
- `engine-v0.7.1`（`344e708150eb158b55144a0228f154ef28f63d6d`）には0.7.0後の#512/#514/#515の実修正があります。正しい座標は**修正版0.7.1**で、0.7.0の内容へ差し戻して上書きしません。本方針では**Engineソースのみの通常リリース**です。GitHub表示と説明文だけを訂正し、tag・ソース・assetは維持します。
- 0.7.1の受け入れ範囲は、後継v17/v30の限定的な修正と、決定論的・合成データの回帰検証、歴史的挙動の維持です。#517のPR CI 23/23・正確なマージ後CI 22/22・ローカルworkspace 1,468成功／失敗0／既存ignore 6。fixtureは20/20・根拠なし受け入れ0、元archiveの13件のハッシュも維持。新しいlive-provider・実ユーザー・独立した人間の承認を検証済みとは主張しません。
- #488/#489/#491は0.7.1の範囲外の保留仮説です。公開CLIは0.5.4 / Engine 0.6.1のままです。#506のCLI 0.5.5 / Engine 0.6.1候補は別工程で、公開前のWindows実機確認が引き続き必要です。Engineソースの昇格で完了扱いにしません。
- 旧Engine/CLIのGitHub区分は、別途レビューしない限り履歴として維持します。過去の全プレリリースを一括で承認し直したり、tag内の固定文書を書き換えたりしません。現在のGitHub説明文と本方針で訂正後の区分を説明します。
